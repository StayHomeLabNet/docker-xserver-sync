# Docker → XServer Sync 製品仕様 v0.1

更新日: 2026-11-07

## 1. 目的

Windows、macOS、Linux 上の Docker 開発環境で管理している PHP サイトを、XServer の指定ディレクトリへ安全に一方向デプロイするデスクトップアプリを提供する。

本製品は常時ミラーリングツールではなく、次の手順を明示的に行うデプロイツールとする。

1. ソースを固定する。
2. XServer と比較して変更計画を作る。
3. ユーザーが計画を確認して承認する。
4. リモートをバックアップする。
5. 一時領域へ転送し、安全な単位で公開する。
6. 結果を検証し、履歴を保存する。

## 2. MVP のスコープ

### 含める

- Windows 11、macOS、主要 Linux デスクトップで動作する PySide6 GUI
- 複数プロジェクトの登録
- Docker の bind mount またはホスト上のプロジェクトディレクトリを同期元として選択
- SSH/SFTP による XServer との接続
- ファイルの追加・更新・リモートのみ・同一・保護対象の判定
- ドライラン、差分表示、明示承認
- 上書き前バックアップ
- 一時ファイル転送後のリネームによるファイル単位の安全な置換
- 通信切断、キャンセル、アプリ異常終了からの回復案内
- 同期履歴と監査ログ

### MVP から除外する

- 既存本番WordPressに対する日常的なMySQL同期・復元
- 双方向同期と競合解決
- ファイル変更のリアルタイム監視・即時反映
- XServer API による契約・ドメイン・SSH 設定変更
- サイト全体を一度に切り替えるリリースディレクトリ方式
- スケジュール実行、無人デプロイ

MySQL は本番側でユーザー操作により更新されるため、通常のデプロイでは同期しない。ファイル同期の操作から誤って DB を変更できない構造にする。例外は、空のXServerへのWordPress初回セットアップと、明示承認されたスキーママイグレーションに限定する。

## 3. 確定する初期方針

| 項目 | MVP の仕様 |
|---|---|
| 同期方向 | ローカル Docker 環境 → XServer の一方向 |
| 起動方法 | ユーザーによる手動実行のみ |
| 同期元 | Docker へ bind mount しているホストディレクトリ |
| Docker Volume | MVP では直接読まない。必要ならユーザーが一時出力する |
| リモート削除 | 既定で無効。リモートのみのファイルは保持して警告表示 |
| 同期前バックアップ | 既定で必須。警告確認後に明示スキップ可能（削除とは併用不可） |
| ドライラン | 承認付き同期では必須。初回用の無条件上書きは独立経路 |
| 計画有効期限 | 15 分 |
| 承認再利用 | 不可。1 計画につき 1 回限り |
| シンボリックリンク | ローカル・リモートとも追跡せずエラー扱い |
| 同時実行 | アプリ全体で 1 ジョブ、同一プロジェクトは常に排他 |
| DB | 通常同期では変更しない。WordPress初回セットアップでのみ専用フローで作成・インポートする |
| 対応サイト | WordPress、Laravel、独自 PHP |
| 依存ライブラリ | `vendor/` をローカルで構築し、コードと共に転送 |
| 正本の分離 | コードはローカル、アップロード・生成物・本番データは XServer |

## 4. 対応環境

- Python 3.12 系
- GUI: PySide6
- 対応 OS: Windows 11、macOS のサポート中バージョン、Ubuntu LTS
- XServer 接続: SSH/SFTP、公開鍵認証、既定ポート 10022
- 設定・履歴: SQLite
- 接続先確認コード: OS の資格情報ストアを利用し、SQLite には参照名だけを保存する
- 秘密情報: 秘密鍵内容とパスフレーズを SQLite やログへ保存しない
- 配布: PyInstaller を第一候補とし、OS ごとにビルドする

OS ごとの資格情報ストアは Windows Credential Manager、macOS Keychain、Linux Secret Service を利用する。確認コードの保存・読み出し・旧SQLiteからの移行に失敗した場合は同期を禁止し、再登録を要求する。秘密鍵のパスだけを保存し、パスフレーズは実行ごとに入力する。

## 5. プロジェクト設定

必須項目:

- 表示名
- サイト種別
- 1 件以上のローカル・リモートパスマッピング
- SSH ホスト、ポート、ユーザー名
- 秘密鍵の参照
- 検証済みホスト鍵フィンガープリント
- 対象ドメイン
- 除外ルール

### パスマッピング

1 プロジェクトは複数の `SyncMapping` を持てる。各マッピングは次を持つ。

- 表示名
- ローカル同期元の絶対パス
- リモート同期先の絶対パス
- 除外ルール
- 保護ルール
- 新規ファイル・ディレクトリのパーミッション
- リモート削除方針（MVP は常に保持）

例:

```text
WordPress:
  local:  C:\sites\example
  remote: /home/server-id/example.com/public_html

Laravel application:
  local:  C:\sites\example
  remote: /home/server-id/example-app
  exclude local subtree: public/

Laravel public:
  local:  C:\sites\example\public
  remote: /home/server-id/example.com/public_html
```

Laravel の具体的な配置は XServer 上の実環境に合わせて設定する。アプリは例のパスを決め打ちしない。

禁止条件:

- 同一プロジェクト内のリモート同期先が互いに包含・重複する。
- ローカル同期元が同じ内容を二重に転送する。
- マッピング先が許可された XServer アカウント領域外にある。
- 保護パスが別マッピングの同期対象として迂回される。

設定保存前に以下を検証する。

- ローカルパスが存在し、読み取り可能である。
- 各リモートパスが空、`/`、ホーム直下、または許可ルート外ではない。
- SSH ホスト鍵が、ユーザーが XServer 管理画面で確認したフィンガープリントと一致する。
- リモートパスに改行、NUL、`.` / `..` セグメントがない。
- ソースと転送先の組が既存プロジェクトと意図せず重複していない。

### 既定の除外ルール

```text
.git/
/.gitignore
/.gitattributes
/.github/
/.gitlab/
/.dockerignore
/.editorconfig
/.idea/
/.vscode/
.env
.env.*
*.pem
*.key
docker-compose*.yml
docker-compose*.yaml
compose*.yml
compose*.yaml
Dockerfile*
node_modules/
/README*
/readme*
/CHANGELOG*
/LICENSE*
/license*
/docs/
/test/
/tests/
/AGENTS.md
/CLAUDE.md
/.phpunit.result.cache
/phpunit.xml*
.DS_Store
Thumbs.db
```

`.env.example` は除外しない。先頭が `/` のパターンは同期元ルートだけに適用し、プラグインやテーマに同名のファイルがあっても除外しない。除外ルールは gitignore 互換構文を採用し、適用結果をドライラン画面で確認できるようにする。

`vendor/` は対象サイトの回答に基づき、既定で転送対象にする。Composer の `--no-dev --classmap-authoritative` 等の実行自体はアプリの責務に含めず、同期元に完成済みの `vendor/` が存在することを事前チェックする。PHP バージョンとプラットフォーム要件が XServer と互換でない場合は同期を禁止する。

## 5.1 サイト種別プリセット

プロジェクト作成時にサイト種別を選択し、保護ルールの初期値を設定する。プリセットは編集可能だが、危険な変更には警告を表示する。

### WordPress

ローカル正本として同期する候補:

- WordPress コア
- `wp-content/themes/`
- `wp-content/plugins/`
- `wp-content/mu-plugins/`
- ローカルで構築した `vendor/`（存在する構成のみ）

XServer 正本として保護する既定パス:

```text
wp-config.php
.htaccess
wp-content/uploads/
wp-content/cache/
wp-content/upgrade/
wp-content/backup*/
wp-content/*-backups/
```

本番の管理画面からテーマ、プラグイン、WordPress コアを更新するとローカル正本と競合する。このため、コードをローカル管理するプロジェクトでは本番のファイル更新を停止する `DISALLOW_FILE_MODS` を推奨し、接続チェックで状態を確認できる場合は警告する。メディア、投稿、設定、ユーザー等は本番 DB と `uploads/` を正本とし、通常デプロイでは変更しない。

### Laravel

ローカル正本として同期する候補:

- `app/`, `bootstrap/`, `config/`, `database/`, `public/`, `resources/`, `routes/`
- `artisan`, `composer.json`, `composer.lock`
- ローカルで本番用に構築した `vendor/`
- ビルド済みフロントエンド成果物

XServer 正本または実行時生成物として保護する既定パス:

```text
.env
storage/app/
storage/logs/
storage/framework/cache/
storage/framework/sessions/
storage/framework/views/
bootstrap/cache/*.php
```

`storage/app/public/` にユーザーアップロードが入る場合は XServer 正本として保護する。`public/storage` はシンボリックリンクであることが多いため同期せず、初回セットアップで別途作成・検証する。MVP はリモートコマンドによる `artisan migrate` やキャッシュ再生成を自動実行しない。

### 独自 PHP

既定で以下を保護する。

```text
.env
config/local*.php
uploads/
storage/
cache/
logs/
tmp/
```

プロジェクト作成時に「本番で書き込まれるディレクトリ」を最低 1 回確認させる。未指定の場合は本番適用前の重大警告とし、ユーザーが明示確認するまで同期できない。

### 保護パスの共通動作

- 保護パスは走査結果に表示するが、追加・更新・削除対象にしない。
- 保護パス配下へローカルファイルが存在してもアップロードしない。
- コードパスでリモート変更を検出した場合は「本番ドリフト」として表示する。
- 通常の承認付き同期では、本番ドリフトを無条件で上書きせず再計画を要求する。
- 保護ルールの解除はプロジェクト設定変更として計画を失効させる。

## 6. 差分検出

変更種別:

- `ADD`: ローカルにのみ存在
- `UPDATE`: 両方に存在するが内容が異なる
- `SAME`: 内容が同一
- `REMOTE_ONLY`: リモートにのみ存在
- `PROTECTED`: ルールにより同期禁止
- `TYPE_CONFLICT`: ファイルとディレクトリなど種類が競合
- `UNREADABLE`: 読み取りまたはハッシュ計算不能

正しさを優先し、最終判定には SHA-256 を使う。サイズと更新日時は走査の高速化に利用できるが、それだけで `SAME` と確定しない。ドライラン作成時に同期対象ファイルをローカルのステージング領域へコピーし、その内容とハッシュを計画に固定する。

リモート走査は読み取り専用の SSH/SFTP 操作で行う。ドライランではディレクトリ、一時ファイル、ロック、バックアップをリモートへ作成しない。

## 7. ドライランと承認

ドライラン結果には以下を表示する。

- 接続先ホスト、対象ドメイン、リモート絶対パス
- 追加、更新、同一、リモートのみ、保護、競合、エラーの件数
- 転送予定バイト数
- ファイルごとの相対パス、種別、サイズ、更新日時、SHA-256
- テキストファイルの差分（サイズ上限 1 MiB、バイナリは対象外）
- 除外されたファイルと該当ルール
- 警告と本番適用を禁止するエラー

本番同期ボタンの有効条件:

1. 計画が 15 分以内である。
2. エラー、型競合、未確認の重大警告がない。
3. 追加または更新が 1 件以上ある。
4. 対象ドメインをユーザーが再入力し、一致している。
5. 「転送先」「変更内容」「バックアップ」の確認欄が選択されている。
6. 他のジョブが動作していない。

承認後にもエンジン側で同じ条件を再検証する。GUI のボタン状態はセキュリティ境界として扱わない。

### 初回用の無条件上書き

無条件上書きは、差分計画、リモート内容照合、永続バックアップ、転送後ハッシュ検証を省略してローカルの同期対象ファイルを上書きする独立経路とする。確認画面ではフォルダー・ファイルのツリーを表示し、チェックしたファイルだけを転送する。SSHホスト鍵照合、除外・保護ルール、本番書き込み先確認、対象ドメイン再入力は省略しない。未選択ファイル、リモートにしかないファイル、保護フォルダーは削除しない。

## 8. 本番同期

本番同期は以下の順序で行う。

1. プロジェクト排他ロックを取得する。
2. 設定ハッシュ、計画期限、承認の未使用を検証する。
3. SSH 接続先とホスト鍵を再検証する。
4. リモートを再走査し、ドライラン時からの変更がないことを確認する。
5. 更新対象の既存ファイルをバックアップ領域へコピーする。
6. バックアップのサイズと SHA-256 を検証する。
7. ステージング済みローカルファイルを、同じリモートディレクトリ内の一時名へ転送する。
8. 転送後の SHA-256 を検証する。
9. 一時ファイルを最終名へリネームする。
10. 全対象を再検証する。
11. 任意の HTTP ヘルスチェックを行う。
12. 履歴を確定し、承認を使用済みにする。

一時名は `.dxsync-{job_id}-{random}.tmp` とする。既存ファイルを直接上書きしない。パーミッションは既存ファイルの値を維持し、新規ファイルは設定可能な既定値（初期値 `0644`、ディレクトリ `0755`）を使う。

## 9. バックアップと復元

バックアップはプロジェクトの同期先外にある専用ディレクトリへ、ジョブ単位で保存する。候補例:

```text
~/.dxsync/backups/{project_id}/{job_id}/
```

保存内容:

- 上書き前ファイル
- マニフェスト（元パス、サイズ、ハッシュ、パーミッション、日時）
- 実行した操作のジャーナル
- 同期計画の署名済みコピー

復元時は、公開側ファイルが同期完了時のハッシュと一致する場合だけ自動復元できる。外部変更がある場合は上書きせず、差分と選択肢を表示する。

保持期間の初期値は 30 日、最大 20 ジョブとし、いずれかを超えた古いものから削除候補にする。自動削除は同期ジョブの成功後にのみ行い、削除内容を履歴に残す。

## 10. キャンセル・障害回復

- 走査中: 即時停止可能
- バックアップ中: 現在のファイル処理完了後に停止
- 転送中: 転送中の一時ファイルを削除して停止
- 公開置換中: 現在のファイル置換を完了し、整合性確認後に停止
- 検証中: 検証を完了してから結果を表示

各操作の前後を SQLite ジャーナルへ記録する。起動時に未完了ジョブを検出した場合、自動再開や自動復元は行わない。「状態確認」「安全な一時ファイルの清掃」「復元」の選択肢を提示する。

## 11. セキュリティ要件

- SSH の `known_hosts` 自動受諾を禁止する。
- ホスト鍵変更時は接続を停止し、再確認を要求する。
- 秘密鍵、パスフレーズ、API キー、`.env` 内容をログへ出さない。
- ログのパスは相対表示を基本とし、必要以上のローカル個人情報を残さない。
- リモート操作は設定済み許可ルート配下に正規化できるパスだけを対象にする。
- シンボリックリンク、ハードリンク、デバイスファイルを同期しない。
- SQL、シェルコマンド、ファイル名を文字列連結で実行しない。
- 計画 JSON は正規化してハッシュ化し、承認後の変更を検出する。

### 安全同期の自動実行

自動実行は読み取り専用ドライランを最初に行い、変更内容、転送先、バックアップ方式、HTTPS確認設定を統合確認画面に表示する。一度の明示承認後に限り、再検証、バックアップ、承認付き同期を自動継続する。対象ドメインの再入力はプロジェクト単位の設定で省略できるが、転送先・変更件数と自動処理内容の確認チェック、および明示承認は省略しない。事前承認や完全無確認の本番書き込みは提供しない。

自動実行設定はプロジェクト単位で保持し、バックアップ方式、REMOTE_ONLY存在時の停止、HTTPS確認パス、最大変更件数・UPDATE件数・転送量、対象ドメイン再入力の要否を含む。REMOTE_ONLYは自動削除しない。計画変更、安全上限超過、再検証失敗、バックアップ失敗、転送失敗では後続処理を実行しない。無条件上書きへ自動的に切り替えない。実行中はプロジェクト、マッピング、接続設定、秘密鍵パス、パスフレーズを変更できない。

長時間処理はワーカースレッドまたは別プロセスで行い、GUI スレッドをブロックしない。数万件の一覧は `QAbstractTableModel` と遅延表示を使う。

## 13. 受け入れ条件

- ドライランでリモート側に書き込みが一切発生しない。
- 除外ファイルと秘密情報が転送対象にならない。
- 未検証または変更されたホスト鍵では接続できない。
- 接続先確認コードがOS資格情報ストアで保護されていない場合は同期できない。
- 計画期限切れ、設定変更、ローカル変更、リモート変更のいずれでも承認が無効になる。
- バックアップの検証に失敗した場合は公開ファイルを変更しない。
- 転送中断時も既存公開ファイルが部分データにならない。
- リモートのみのファイルは既定で削除されない。
- WordPress の `wp-content/uploads/`、Laravel の実行時 `storage/`、独自 PHP の指定書き込み領域が変更されない。
- 通常のファイル同期で MySQL への接続・書き込みが発生しない。
- `vendor/` 内のファイルが通常コードと同じ計画・バックアップ・検証手順で転送される。
- 同一プロジェクトの同時同期ができない。
- 異常終了後に未完了ジョブを検出できる。
- 外部変更済みファイルを復元で無断上書きしない。
- Windows、macOS、Linux で同一の計画から同一の差分判定になる。

## 14. 実装順序

1. ドメインモデル、設定、SQLite スキーマ
2. ローカル走査、除外、ステージング
3. SSH/SFTP 接続と読み取り専用リモート走査
4. 差分計画と CLI ベースのドライラン
5. PySide6 のプロジェクト設定・差分画面
6. 承認、バックアップ、一時転送、置換
7. ジャーナル、障害回復、復元
8. HTTP 検証、履歴、ログ
9. 3 OS のパッケージングと E2E テスト

GUI より先に同期エンジンを UI 非依存の Python パッケージとして実装する。CLI は開発・テスト用インターフェースとして残す。

## 15. 確定済みの環境条件と残る判断

確定済み:

- WordPress、Laravel、独自 PHP のすべてを扱う。
- 同期元は Docker へ bind mount されたホストディレクトリである。
- XServer 側で画像、問い合わせ、管理画面操作等によるファイル・DB 更新がある。
- `vendor/` はローカルで構築して転送する。

このため、サイト全体の完全ミラーではなく、コード領域と本番可変領域を分離する方式を採用する。

MVP 着手後、実サイトを登録する際にプロジェクト単位で決める項目:

1. ローカルルートと公開ルートの対応関係。
2. WordPress の本番管理画面からコード更新を許可するか。
3. Laravel の `storage/app/public/` を含む、本番書き込み領域。
4. 独自 PHP のアップロード、キャッシュ、ログ、生成ファイルのパス。
5. リモートのみのコードファイルを将来削除する必要があるか。
6. 同期後の正常性を判定できる URL と期待する HTTP ステータス。
7. 1 プロジェクトあたりのおおよそのファイル数、総容量、最大単一ファイルサイズ。
8. XServer の PHP バージョンと、`composer check-platform-reqs` 相当の互換性確認方法。

## 16. MySQL を追加する場合の判断基準

- XServer 側でデータが更新される場合、開発 DB の全量上書きを通常操作として提供しない。
- スキーマ変更はフレームワークのマイグレーションを第一候補とする。
- 初回移行や明示的な環境再作成だけを、DB 全量置換の候補とする。
- ファイルと DB を同時変更する場合、同じリリース ID と復元手順で一組として管理する。
- DB 機能は別の危険操作モードとし、ファイル同期の承認だけでは実行できない。

現在の条件では XServer 側 DB が本番正本である。WordPress の投稿・設定・ユーザーや、本番の問い合わせデータをローカル DB で上書きしてはならない。

MySQL の将来機能は以下に分離する。

1. **スキーマ変更:** Laravel 等のバージョン管理されたマイグレーション。
2. **初回移行:** 空の本番 DB へ明示的にデータを投入する危険操作。
3. **本番バックアップ:** 読み取り専用で取得し、ローカルへ暗号化保存する操作。
4. **選択データ移送:** 要件ごとの専用処理。汎用的な双方向同期にはしない。

WordPress の通常デプロイでは DB ダンプを送らない。プラグインやテーマの更新が DB マイグレーションを要求する場合は、デプロイ後の管理画面または専用手順で実行し、ファイル同期とは別の承認記録を持たせる。
